Headline

Wall clock per task

Warning — run-to-run spread is larger than the model difference

The same 3B model on the same task ran 19.6 s once and 50.7 s the next time. Two runs is not enough to separate model from noise, so treat any per-task gap below roughly 2× as unmeasured rather than real.

The cost/quality plane

Read the 8B's miss as a clock failure, not a competence failure

The 8B lost write-function to budget_exhausted at 402 s against a 300 s cap. It was not marked wrong — it ran out of time while still working. Give that task a larger budget_seconds and the pass rate may well return; what will not change is that it needs roughly 2.3× the wall clock to get there. On this hardware that is the whole story, because seconds are the budget.

The money axis is omitted because it has one value

Every arm ran locally, so cost is $0.0000 throughout. A cost-versus-quality plot would be a vertical line. Wall clock stands in as the binding budget — which is what the build spec predicts for a CPU tier, now measured rather than assumed.

What these numbers cannot support

  • Not a pass rate. Four tasks means one task is 25 percentage points. 4/4 is consistent with a true rate anywhere from roughly 40% upward, and 3/4 is not reliably different from 4/4 at this n.
  • Not "the 8B is worse at coding." Its one miss was a clock expiry mid-work, not a wrong answer. The defensible claim is about seconds: ~2.3× the wall clock of the 3B, measured.
  • The verifiers check shape, not truth. Three of the four tasks are scored by json_schema, which accepts {"total": 0} for an invoice whose real total is 4825. A wrong answer of the right shape passes. Read 4/4 as "produced well-formed output four times," nothing stronger.
  • Cache hit ratio is not measured here. It reads 0.00 for every local run because the Ollama adapter reports no cache-token counts — absent instrumentation, not a collapsed discount. The cache invariant is covered by the acceptance test instead.
  • The suite is a shape demo. Four tasks written to exercise the harness. The 30-task suite that would carry a real claim does not exist yet, and it is the denominator of every number above.
  • Single run per arm, except 3B. Only the 3B has a repeat, and that repeat is what exposed the variance warning above.

What it does establish

  • The whole pipeline runs end to end with no API key and nothing billed — plan, gate, deputy, receipts, hash chain, telemetry.
  • Every model call is accounted for in calls, and every task's chain verifies against the anchor afterward.
  • Bigger is not automatically better here. The 8B is slower on every single task and finished with a lower pass rate. Nothing in this suite rewarded the extra parameters enough to pay for the seconds — which is the concrete version of the spec's claim that a smaller model is not automatically a cheaper one, run backwards.
  • The budget mechanism does what it says. A task that overran its wall-clock allowance was stopped and recorded as budget_exhausted rather than left to run — visible in the table, not buried.
