# Independent audit — 2026-09 (desktop-app @ 8fe0442)

Auditor came to the code cold. Windows 11, Python 3.11.15. Full suite green at
entry: **1021 passed, 25 skipped, 535 s**. Every finding below has a runnable
demonstration under `docs/evidence/audit-2026-09/`; run them with

```
set PYTHONUTF8=1 && set PYTHONIOENCODING=utf-8
python -m pytest docs/evidence/audit-2026-09/ -q -p no:cacheprovider -o pythonpath=src
```

A finding marked "green = demonstration" asserts the CURRENT behaviour, so a
passing evidence test IS the proof; a fix turns it red. Probes that are scripts
(`probe_*.py`, `measure_*.py`, `close_timer.py`, `shutdown_parts.py`) print
their evidence and are quoted inline.

This project already documents its own sandbox as advisory (D32) and its POSIX
paths as never-run (PLATFORMS.md). Neither is reported as a finding. What is
reported is behaviour weaker than documented, or a surface the docs do not cover.

## FINDINGS (ranked)

### F1 — HIGH — a Telegram callback decides approvals that are not the channel's
*Class: DR1 width (a control scoped narrower than what it protects) / adjacency.*

`TelegramBot._handle_callback` (`src/agent/channel/telegram.py:368`) re-verifies
the **sender** against the allowlist (correct, inv. 68) and then calls
`ctx.resolve_approval(approval_id, ...)` on whatever id the callback names. It
never checks that the approval belongs to a task bound to this channel. So an
allowlisted (or compromised-allowlisted) Telegram sender can approve or deny a
**local** task's parked action — one that `resend_pending()` correctly refuses
to ever push to a phone (`_chat(task_id) is None`). The allowlist guards *who
may press a button*; it does not guard *which decisions this channel owns*.

Attacker: an allowlisted sender, or someone who has taken over that account.
The approval preview a local operator was about to read at their own keyboard
is decided from the phone instead, and `run(task_id)` is invoked for approvals.

EVIDENCE: `test_audit_channel.py::test_F_channel_callback_decides_a_local_tasks_approval` (passes).
```
resend_pending() == []            # never asked the phone
handle_update(callback(aid)) -> {'action': 'approve', 'task_id': <local task>}
approvals.status == 'approved'
```

### F2 — HIGH — any local process obtains the console bearer token with no credential
*Class: new class (trust-boundary assumption narrower than the deployment).*

`control/guard.py` `AccessGuard.dispatch` lets `GET /` through for any loopback
Host with no token (`server.py:503` then injects the token into the HTML). The
documented rationale (guard.py:1-27, ui.html:362) is precise but covers exactly
one attacker — a **cross-origin web page**, which same-origin policy stops from
reading the response. It does **not** cover another **local process or local
user**: any program that can open a socket to the port issues `GET /` and reads
`__ALPHA_TOKEN__` out of the body, then drives every authenticated route
(rewrite the reviewer policy, add skills, start runs, decide approvals). On a
shared or multi-user Windows box, "loopback + a page can't read it" is not the
same boundary as "only the console user can act."

EVIDENCE: `test_audit_control.py::test_F_unauthenticated_loopback_get_returns_the_token` (passes) — `GET /` with no `Authorization` and no `Origin` returns 200 with the token in the body.

Related, same file: the token persists to `.alpha_token` in `ctx.config.root`.
In **checkout mode** that root is the repository directory — here, under
`OneDrive\Desktop\…`, so the live bearer token (and `agent.local.db` with every
task goal and answer) is continuously synced to a third-party cloud. `.gitignore`
lists `.alpha_token` but `.gitignore` does not stop OneDrive. The desktop app
avoids this by forcing platformdirs state (`desktop.py:45`); running `alpha
serve` from the checkout does not. Trigger: developer usage from a synced folder.

### F3 — MEDIUM — the sandbox's "no network" guarantee is not enforced
*Class: inert guarantee / DR3 (a promise with no route guarded).*

`execute/libraries.py:22` states the sandbox's three promises: "no network, no
writes outside `artifact_scope`, no subprocesses," and `register()` refuses any
library declaring `uses_network`. The audit hook in `sandbox.py` enforces the
write fence, the read fence, spawn denial and the SQLite fence — but has **no
`socket`/connect event**, so model-written code opens outbound sockets freely.
The exfiltration path the whole taint system exists to prevent (untrusted data
+ a way out) is open at the code layer, whichever way `web_fetch`'s taint gate
is set. This is *weaker than documented*, which is in scope even though the
sandbox is advisory: the advisory hook already polices writes, reads, spawns
and SQLite; network is the one promise made and not policed.

EVIDENCE: `test_audit_sandbox.py::test_F_sandbox_has_no_network_fence` (passes) — sandboxed code connects to a loopback listener and sends bytes; `run_sandboxed(..., protected_paths=…)` returns them received.

### F4 — MEDIUM — `descendants()` adopts recycled PIDs; a DR5 sibling of the reap-parentage fix
*Class: DR5 (unswept sibling) / process leak.*

`proc.orphan_pids` was hardened (module docstring, inv. reaper-parentage) to
compare parent/child **start times** so a recycled PID is not mistaken for a
live parent. `desktop.py:102 descendants()` — the function `shutdown()` uses to
kill everything on window close — walks the same `(pid, ppid)` table with **no
start-time check**. A process whose recorded `ppid` has died and been recycled
to the desktop app's PID would be pulled into the kill set; taskkill `/T /F`
(windows.py:21) then takes it and its whole tree. Same bug, same table, the
copy the sweep missed.

EVIDENCE: `probe_descendants_pid_reuse.py` (read-only; kills nothing):
```
303 processes; 0 with a recycled 'parent' pid          # not live on this box right now
17 live processes name a dead parent pid, e.g. [('csrss.exe',1176),('wininit.exe',1176),…]
fake table: descendants() = [4242] -> shutdown() would kill_tree(4242)   # decision reproduced
```
The last line drives the real `descendants()` over a table where the app's own
PID was recycled from explorer's dead parent; it returns explorer's PID, which
`shutdown()` would kill. Not observed firing in the wild (PID reuse is needed),
so the exposure — 17 live processes with a dead recorded parent — is shown, and
the decision is shown reproduced.

### F5 — MEDIUM — the planner survey reads protected state into the prompt, bypassing the gate
*Class: DR3 (a control guarding one route to the bytes).*

`gate_tool_call` refuses `read_file` of anything in `PROJECT_STATE`
(`.alpha_token`, `.env`, databases, graders…). `plan/planner.py:88
_read_only_survey` reads every `artifact_scope` entry **directly** —
`p.read_text()[:2000]` — with no `is_protected` check, and pastes it into the
planner prompt. A task whose scope names a protected file (a console task, or a
suite imported from a folder) leaks that file's first 2000 bytes to the planner
model, through the one file route the gate does not cover.

EVIDENCE: `test_audit_phase.py::test_F_planner_survey_reads_protected_state_into_the_prompt` (passes) — `read_file('.alpha_token')` is denied by the gate, then `draft_plan` puts `SENTINEL-TOKEN-1234` from that same file into the model tail.

### F6 — MEDIUM — memory integrity never consults the hash chain it calls "the authenticated record"
*Class: inert guarantee / DR7 (a check that cannot fail against its stated attacker).*

`memory/store.py:208` says the chain is "the AUTHENTICATED record… cannot be
rewritten," and every `memory.written` event carries the file fingerprint.
But `check_fingerprint` and `verify_memory`/`verify_all` compare tier-1 files
only against `.fingerprint` — a plain sha256 kept **in the same directory as the
files it certifies**. Anything that can edit `MEMORY.md` can rewrite
`.fingerprint` in the same motion; the load-time check reads INTACT, `/alerts`
stays silent, and the poisoned line loads into every future prefix. The chained
fingerprint that would disagree is written by nothing on the read side. Invariant
43's own test only checks that the *file hash changes*, not that any code
compares it to the chain. (The docstring is honest that this is "unaccounted
change, not authenticated tampering" — the finding is that the code presents
`.fingerprint` as the memory-integrity control while the authenticated one it
advertises is never read.)

EVIDENCE: `test_audit_gate.py::test_F_memory_integrity_never_consults_the_chain` (passes) — file + `.fingerprint` rewritten together; `check_fingerprint == INTACT`, `verify_all` reports no `__memory__` finding, and the injected line is in `freeze_memory()["memory"]`, while the chained fingerprint disagrees.

### F7 — LOW/MEDIUM — the console is framable: no `X-Frame-Options`, no CSP
*Class: new class (clickjacking of an irreversible control).*

`GET /` returns the token-bearing console with no `X-Frame-Options` and no
`Content-Security-Policy frame-ancestors`. A frame/navigation request carries no
`Origin` header and its Host is the loopback name, so it passes the guard exactly
as a top-level load does. Any page in the user's browser can frame the working
console and clickjack "Approve and run" / "Allow this once" (a UI whose whole job
is a human's irreversible click). Severity is bounded by needing the port, which
is OS-chosen for the desktop app.

EVIDENCE: `test_audit_control.py::test_F_console_is_framable` (passes).

### F8 — LOW — plausible planner output crashes `parse_plan` with a 500 and logs model text
*Class: DR4-adjacent fail-open of error handling / robustness.*

`parse_plan` (`planner.py:105`) degrades gracefully only when **no** JSON is
found. JSON a 3B model plausibly emits — `est_tokens:"about 500"`,
`action_mode:"python"`, `max_taint_out:"low"`, a bare-string step, `tools:5` —
raises `ValueError`/`ValidationError`/`AttributeError`/`TypeError` out of
`draft_plan`. `POST /tasks/{id}/plan` has no handler for it, so it is a 500, and
the traceback (carrying the model's raw output) is written to the server log —
`desktop.log` in the windowed build (see §Inefficiency/logging). Not a security
hole by itself; it is an entry point whose realistic failure is unhandled.

EVIDENCE: `test_audit_phase.py::test_F_plausible_planner_output_crashes_parse_plan` (5 params, all pass).

### F9 — LOW — a non-ASCII credential is a 500, not a 401
*Class: DR7-adjacent (a check that raises instead of returning false).*

`guard.py:137/143` feeds the supplied token straight to
`secrets.compare_digest`, which raises `TypeError` on a non-ASCII `str`. A token
supplied in the query string (`?token=café`) is non-ASCII on the wire and turns
an auth *failure* into a server error. Trivially reachable, no auth needed.

EVIDENCE: `test_audit_control.py::test_F_non_ascii_token_header_is_a_500_not_a_401` (passes, asserts the `TypeError`).

## HYPOTHESES (unranked — not demonstrated end-to-end)

- **H1 — `esc()` is unsafe inside a JS-string-in-an-HTML-attribute.** ui.html
  builds `onclick="delSuite('${esc(s.id)}','${esc(s.name)}')"`. `esc()` encodes
  `'` as `&#39;`, but the browser HTML-decodes an attribute value *before* the JS
  parser sees it, so a suite name of `x');alert(1);('` round-trips a quote back
  into script. `test_audit_control.py::test_F_esc_is_not_safe_inside_js_string_in_attribute`
  proves the decode round-trip. Not ranked because I did not confirm a stored
  suite/grounding/skill name reaches that sink without a second server-side
  validation, and suite names are author-supplied (the console user attacking
  themselves), so the realistic vector is a name imported from a folder or set
  via the API by F2's local caller. Worth closing as self-XSS-or-worse.

- **H2 — spawn denial misses `_winapi.CreateProcess`.** The sandbox `_SPAWN`
  list (`sandbox.py:187`) names `subprocess.Popen`, `os.system`, `os.exec*`,
  `os.spawn*`, `os.posix_spawn`, `os.startfile` — not `_winapi.CreateProcess`,
  the Windows primitive `subprocess` sits on. `test_audit_sandbox.py::test_F_spawn_denial_misses_winapi_createprocess`
  shows `Popen` refused while a direct `_winapi.CreateProcess("cmd /c exit 7")`
  runs to exit 7 inside the sandbox. Ranked as a hypothesis, not a finding,
  because the child is still born inside the Job Object (its limits and
  KILL_ON_JOB_CLOSE apply) and the sandbox is advisory by construction (D32) —
  so this weakens the *spawn* promise but not the kernel limits. It is
  nonetheless a documented promise ("no subprocesses") with a bypass, and the
  `os`-level fix would not cover it.

## INEFFICIENCY (measured)

### I1 — the 188 MB build is ~66% two numeric libraries the product never imports at runtime
`du` of `C:\Users\char1\.alpha-build\dist\alpha` = **193 MB** (the "188 MB" in
docs; `alpha.exe` alone is 36 MB after UPX). By `_internal/`:

| component | MB on disk | in PYZ (compressed) |
|---|---|---|
| scipy + scipy.libs | 48 + 20 | 3.9 |
| sympy | 26 (25.6 MB of it is 1501 `.py` files **also present in the PYZ** — shipped twice) | 13.9 |
| numpy + numpy.libs | 6 + 21 | 1.4 |
| mpmath | 2 | 0.9 |
| pygments (via rich) | — | 1.7 |
| anthropic | — | 1.6 |
| textual | — | 1.3 |
| _pytest/pluggy | (probe build only) | 0.7 |

`scipy` is imported for exactly one call: `from scipy.stats import binomtest`
in `skills/gate.py:218` (McNemar). `sympy`/`mpmath` are a **sandbox library**,
not product code — the model may `import sympy`, so it must be present for the
sandbox interpreter, but `--collect-all sympy` bundles its data twice (once as
`.py` files under `_internal/sympy`, once compiled into the PYZ) and pulls all
of scipy/numpy transitively. Removable without changing what the model can do:
the duplicate `sympy` source tree (`--collect-submodules` instead of
`--collect-all`, ~25 MB), and `binomtest` reimplemented from `math`
(`scipy`+`numpy`+libs ≈ 95 MB) — a one-sided binomial tail is `sum(comb(n,k)…)`.
Combined headroom ≈ **120 MB of 193 MB.** EVIDENCE: `measure_prefix.py` output
above and `du`/PYZ dumps in this section were produced with the build venv's
`PyInstaller.archive.readers`.

### I2 — the ~8 s window-close is `kill_tree`, not uvicorn
Closing the window took **7.95 s** end to end (`close_timer.py`, frozen app with
scratch state). Broken down (`shutdown_parts.py`):

```
server stop (idle keep-alive client): 0.22 s
alive() one tasklist call:            0.42 s
kill_tree(dead pid):                  0.94 s
kill_tree x6 live children serially:  5.85 s
```

uvicorn stops in ~0.2 s. The cost is `shutdown()` → `kill_tree` per descendant,
**serially**, each spawning `taskkill` and then polling `tasklist` every 0.2 s
until the pid is gone (`proc.kill_tree`, `windows.py:27 alive`). Six children
(one webview → its GPU/renderer/utility helpers) = ~6 × ~1 s. Fixes without
behaviour change: KILL_ON_JOB_CLOSE already kills sandbox trees when the job
closes, so `descendants()` at shutdown is largely redundant for those; and a
single `taskkill /T /F` on the app's own PID kills the whole tree in one call
rather than N. The per-pid poll loop is the dominant term.

### I3 — prefix tool schemas: 1215 tokens; code-as-action contract delta: 41 tokens
`measure_prefix.py`: 17 tools → **1215** est tokens of JSON schemas (the "~966"
in D33 predates added tools), plus **464** tokens of tool manual. `system_contract`
with code-as-action on vs off differs by **41** tokens — the "+150 per call when
unused" figure in FINDINGS 1.29 is the runtime cost of the model *emitting* code
blocks it did not need, not the static prefix, and is consistent. These are
per-step costs on a CPU-bound local model whose binding budget is wall clock; the
schemas re-process on every step. The D33 decision not to move tier-1 out of the
system block stands (its trigger metric is still 0).

### I4 — test suite 535 s; `test_cli_subcommands.py` dominates
25 subprocess CLI tests each cold-start the frozen-import-heavy CLI: the top 20
durations are all `test_cli_subcommands.py` at 4–14 s each, ≈ **170 s (32%)** of
the run, plus `test_the_wheel_ships_no_tasks` setup 12 s (builds a wheel) and
`test_desktop` 9 s. These are subprocess-per-test by design (inv. 115); a
session-scoped scratch install shared across the read-only ones would reclaim
most of it. Tombstone growth (B4) is already bounded — `compact.py:80
TOMBSTONE_SHARE` folds the oldest into one index; not a current inefficiency.

## WHAT WAS CHECKED AND FOUND CLEAN

- **Frozen exe as interpreter (B2).** `alpha.exe --alpha-sandbox-child -c "…"`
  does run arbitrary Python as the user and writes anywhere (confirmed:
  wrote `~/.alpha_probe_marker_audit`, deleted after). This is by design — it is
  the sandbox's interpreter, and `CHILD_ENV`/`SANDBOX_CHILD_FLAG` exist to stop
  the frozen app **re-launching itself as the app** (recursion, C26), not to
  sandbox the child (the Job Object + guard template do that, applied by the
  parent). Reachable by "anything that can exec the binary," but that confers no
  privilege beyond running any Python already on the machine, so not ranked. The
  env marker protects against recursion and app-relaunch-from-sandbox; it does
  **not** make a flag-invoked child sandboxed — worth stating in `frozen.py`.
- **Read fence allowlisting the exe (B2).** `sandbox.py:171` adds `sys.executable`
  as a single **file**, only when frozen, not its directory — confirmed narrowest
  form; unfrozen the interpreter is already under `base_prefix`.
- **DNS rebinding / CSRF / Host / Origin (B2).** Host allowlist refuses absent
  and non-loopback Host (guard.py:343, inv. 94); Origin refused when cross-site;
  bearer token is the CSRF stop and a cross-origin page cannot read `/`. All hold
  except the local-process case (F2) and framing (F7).
- **pywebview JS bridge (B2).** The app calls `webview.create_window(url=…)` with
  **no `js_api` and no `expose()`** (`desktop.py:150`); `window._functions`/
  `_js_api` are empty, so the bridge exposes only pywebview's own built-ins over
  its private channel. Nothing of the agent is reachable from page JS.
- **desktop.log (B2).** Created only when stdout/stderr are None (windowed build),
  at `%LOCALAPPDATA%\…\desktop.log`, user-profile-scoped. It captures uvicorn
  logging at `warning` and uncaught tracebacks (so F8/F9 land here) — no tokens
  or prompts in the normal path. On this run it was 0 bytes.
- **Grader-to-model routes (B2).** Re-checked all five: prompt allowlist
  (inv. 119, `x-` stripped at depth), feedback (`mesh.feedback_for_model` held
  out under measurement), search index (`search.py` indexes goal+criterion only,
  not `contract_json`; results forced UNTRUSTED), reviewer transcript
  (`context.py:600` pops `detail`, and `score` when held out), filesystem
  (`task_state_paths` protects `grader_dir`). No new route found.
- **Memory as an injection surface (B2).** Untrusted content cannot enter tier 1
  (`memory_write` USER ceiling, inv. 42) — confirmed. The gap is detection, not
  ingress (F6).
- **SQLite routes from sandboxed code (B2).** `_sqlite_targets` handles `file:`
  URIs, `//host/p`, `/C:/`, percent-encoding; authorizer denies ATTACH with an
  unknown target (DR4) and VACUUM INTO; `enable_load_extension` denied. The
  documented residual (a `Connection` built another way, `set_authorizer(None)`)
  is the advisory limit, not a new hole.
- **Taint end-to-end (B3).** `args_taint({})` is TRUSTED — noted under DR4 below,
  but the injection case (untrusted arg to a side-effecting tool) is correctly
  refused by the ceiling.
- **`ctx.web_fetcher` (DR2).** Correctly left **unset** (`context.py:104 = None`);
  the real provenance fetcher is the live default. Not the C34 shape.
- **Channel/schedule tool floors (DR4).** `allowed_senders` empty = nobody
  (telegram.py:257, verified); `CHANNEL_DENIED`/`SCHEDULE_DENIED` are constants;
  unattended origins get no scoped-write fast path (capabilities.py:292).
- **Process leaks from the desktop app (B3).** Window close left **0**
  descendants alive (`close_timer.py`: "descendants still alive after exit: []");
  no `alpha.exe` remained. The leak risk is F4's mis-targeting, not survival.

### DR4 note (not ranked — pre-existing gate shape)
`TaintTracker.args_taint({})` returns **TRUSTED**, and a side-effecting,
non-trusted-tier tool called with no arguments is `allow`ed outright while the
same tool naming its default parks (`test_audit_gate.py`, both pass). Today the
only no-arg side-effecting tool is `memory_consolidate`, which evicts tier-1
entries — a real if minor unattended mutation, and `_effective_args` fills
`_PATH_KEYS` defaults but not non-path defaults like `tier`. It is the "empty
means the most-trusted thing" shape DR4 warns about, in the taint layer rather
than an allowlist. Also noted: the human approval **preview** truncates to ~80
chars of the first argument (`render_preview`, capabilities.py:310), so a
`run_code` approval shows the program's harmless header and hides the tail
(`test_F_human_sees_77_chars_of_run_code`) — the human signs bytes they cannot
see.

## Phase C addendum (2026-09-25, written after this audit, by the builder)

The report above is unedited. What happened next:

- **F1 fixed.** A callback decides an approval only if its task is routed to
  this channel, to the chat the button was pressed in (`channel/telegram.py`).
- **F2 fixed.** `GET /` no longer carries the token. The launcher that owns it
  (the desktop app, or the link `alpha serve` prints) passes it in the URL
  fragment, which never reaches a server; the page keeps it for the tab only
  and strips it from the address bar. Checked in a real browser: a fresh open
  and a same-page paste both authorise; the token is absent from the DOM.
- Both with tests shown red first: `tests/test_audit_2026_09.py`.
- The demonstrations for F1 and F2 now FAIL, as they should. So does F7's,
  because it asserted the framed page carried the token - it no longer does,
  which is why F7 is filed low (D45).
- Mediums, lows, hypotheses and measured inefficiencies: `docs/DEFERRED.md`
  D40-D53, each with its severity from this report.
